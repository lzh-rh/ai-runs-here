When a service alert fires, your team sees a symptom. You still need to find the cause and choose a safe response. Agentic troubleshooting organizes the investigation, review, approved action, and recovery check as Kubernetes resources your team can inspect.

This guide follows an example alert: `ServiceErrorRateHigh` is active for `storefront-api`. You will trace the work across the main components and the Kubernetes resources they share. The example YAML teaches the workflow; use your environment's installation manifests for deployment.

<ArticleCallout variant="important" title="Start with evidence from your cluster">
  <p>Different problems can trigger the same error-rate alert. During a real incident, review the alert, logs, metrics, events, and recent changes before deciding what caused it. Use the <code>storefront-api</code> scenario to learn how the workflow operates.</p>
</ArticleCallout>

## What you will learn

- How the Alerts Adapter turns an active alert into an `AgenticRun` work record.
- What each component does during analysis, approval, execution, and verification.
- How to read the key fields in the example YAML.

## Follow a service error-rate alert

Suppose a service starts returning more failed requests than usual. Its error rate crosses the configured threshold, and `ServiceErrorRateHigh` becomes active.

  <li><span>The service error rate crosses its alert threshold.</span></li>
  <li><span><strong>ServiceErrorRateHigh</strong> becomes active.</span></li>
  <li><span>The Alerts Adapter creates an <strong>AgenticRun</strong> for an eligible alert.</span></li>

The alert starts the investigation. Your team must still establish the root cause, and the workflow provides a consistent way to collect evidence before anyone approves an action.

## Understand what happens behind the scenes

The components exchange Kubernetes objects through the Kubernetes API. Those objects provide the handoff between the Alerts Adapter and the Lightspeed Agentic Operator.

<AgenticWorkflow />

### Read the flow from top to bottom

1. **Alertmanager → Alerts Adapter:** The Adapter checks Alertmanager at set intervals for active alerts.
2. **Alerts Adapter → AgenticRun:** For each alert that passes its rules, the Adapter creates a Kubernetes work order.
3. **AgenticRun → Lightspeed Agentic Operator:** The Operator watches that work order through the Kubernetes API.
4. **Lightspeed Agentic Operator → analysis sandbox:** The Operator creates a temporary worker to investigate and propose options.
5. **Analysis → approval gate:** The proposal waits when the `ApprovalPolicy` requires a person to decide.
6. **Lightspeed Agentic Operator → execution sandbox:** After approval, the Operator creates a new worker for the approved action. Kubernetes RBAC limits that worker to the permissions granted for the action.
7. **Lightspeed Agentic Operator → verification sandbox:** After execution, the Operator creates a separate worker to check recovery.

Each sandbox returns a result for its stage. The Operator saves those results and the run's conditions in the Kubernetes API.

The Adapter creates the work order in the Kubernetes API. The Operator watches the work order and creates the sandbox Pods. The Adapter and the sandbox Pods do not need a direct connection because they share information through the API.

## Meet the workflow components

The next six sections define each component's job and boundary.

### 1. Alertmanager: route an alert to a receiver

Alertmanager receives firing alerts and evaluates routing rules. A rule can use an alert label, such as `severity`, to select a named receiver.

```yaml
route:
  receiver: default
  routes:
    - matchers:
        - severity="critical"
      receiver: your-alert-receiver

receivers:
  - name: default
  - name: your-alert-receiver
```

In this example, `severity="critical"` is the matching condition, and `your-alert-receiver` is the selected destination. Severity describes urgency. A receiver identifies where Alertmanager sends the alert. The root `default` receiver catches alerts that do not match a more specific route.

The Alerts Adapter later compares that receiver name with `filtering.allowedReceivers`. Replace `your-alert-receiver` in both places with a receiver name from your own Alertmanager routing configuration.

### 2. Agentic Alerts Adapter: the translator

Think of the Alerts Adapter as an intake clerk. It:

1. checks Alertmanager at a configured interval for firing alerts;
2. checks each alert's receiver, severity, age, and previous runs;
3. creates one `AgenticRun` in `openshift-lightspeed` for each alert that passes those rules.

Polling means checking for new data at set intervals. On each check, the Adapter reads current alerts and existing runs. It can find an alert that remains active after a restart without keeping its own database.

The Adapter copies the alert name, severity, summary, description, and affected namespace into the work record. It also records identifiers that help it avoid duplicate work for the same alert occurrence.

The Adapter's job ends after it creates the `AgenticRun`. The Agentic Operator and sandbox workers handle diagnosis, approval, execution, and verification.

#### Read the Adapter Deployment YAML

The Adapter runs as a Kubernetes Deployment. This example shows the main pieces and their connections. Supply the image, service account, and Alertmanager address for your environment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lightspeed-agentic-alerts-adapter
  namespace: openshift-lightspeed
spec:
  replicas: 1
  selector:
    matchLabels:
      app: lightspeed-agentic-alerts-adapter
  template:
    metadata:
      labels:
        app: lightspeed-agentic-alerts-adapter
    spec:
      serviceAccountName: <adapter-service-account>
      containers:
        - name: adapter
          image: <adapter-image>
          env:
            - name: ALERTMANAGER_URL
              value: <alertmanager-service-url>
          volumeMounts:
            - name: config
              mountPath: /etc/alerts-adapter
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: alerts-adapter-config
```

<div className="article-table" tabIndex={0} role="region" aria-label="Alerts Adapter Deployment fields">

| Important field | Why it matters |
| --- | --- |
| `namespace` | Places the Adapter beside the Agentic components. |
| `replicas: 1` | Runs one Adapter Pod. After a restart, it reads alerts and existing runs from the APIs again. |
| `selector.matchLabels` and `template.metadata.labels` | The matching label lets the Deployment identify and manage its Pod. |
| `serviceAccountName` | Gives the Pod a Kubernetes identity. RBAC rules grant this identity access to the resources it needs. |
| `image` | Selects the Adapter image that your environment provides. |
| `ALERTMANAGER_URL` | Gives the Adapter the address of the Alertmanager service that it checks for firing alerts. |
| `configMap`, `mountPath`, and `readOnly` | Mount `alerts-adapter-config` inside the container at `/etc/alerts-adapter` without allowing the container to change the file. |

</div>

#### Understand the Alerts Adapter configuration

The Adapter reads its settings from a Kubernetes `ConfigMap`. The configuration has two layers:

1. The outer YAML creates the `ConfigMap` object.
2. The `data.config.yaml` value stores the Adapter's configuration as YAML text.

This example sets `preRunDelay` to two minutes, so an alert must remain active for that long before the Adapter creates a run. It accepts alerts that Alertmanager routes to `your-alert-receiver`.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: alerts-adapter-config
  namespace: openshift-lightspeed
data:
  config.yaml: |
    pollInterval: 30s
    preRunDelay: 2m
    postRunDelay: 1h
    filtering:
      allowedReceivers:
        - your-alert-receiver
    deduplication:
      ignoredLabels:
        - pod
        - instance
```

#### Read the outer ConfigMap

<div className="article-table" tabIndex={0} role="region" aria-label="Outer ConfigMap fields">

| Field | Meaning |
| --- | --- |
| `apiVersion: v1` and `kind: ConfigMap` | Create a standard Kubernetes ConfigMap for non-secret settings. Store passwords and tokens in a Secret instead. |
| `metadata.name` | Names this ConfigMap `alerts-adapter-config`. The Adapter Deployment expects that name. |
| `metadata.namespace` | Places the configuration in the same namespace as the Adapter. |
| `data` | Starts the ConfigMap section that holds keys and values. |
| `config.yaml` | Creates a key named `config.yaml`. The vertical bar stores the indented lines as one block of text. The Adapter reads that text as its own YAML configuration. |

</div>

#### Read the inner `config.yaml`

<div className="article-table" tabIndex={0} role="region" aria-label="Alerts Adapter settings">

| Field | Meaning |
| --- | --- |
| `pollInterval: 30s` | The Adapter checks for active alerts every 30 seconds. |
| `preRunDelay: 2m` | An alert must keep firing for two minutes before the Adapter creates a run. This can ignore short-lived alerts. |
| `postRunDelay: 1h` | After a terminal run, the Adapter waits one hour before creating another run for the same problem. |
| `filtering.allowedReceivers` | Lists the receiver names that the Adapter accepts. Replace `your-alert-receiver` with a name from your Alertmanager routing configuration. Severity labels belong in Alertmanager matchers rather than this list. |
| `deduplication.ignoredLabels` | Leaves changing labels, such as a pod name, out of the problem identifier. This helps one incident remain one incident when a pod is replaced. |

</div>

By default, the Adapter polls every 30 seconds, starts with no pre-run delay, and waits one hour after a terminal run before creating another run for the same problem. This example changes only the pre-run delay. The Adapter checks the Kubernetes API for existing runs on every poll instead of keeping its own database.

### 3. AgenticRun: the shared work order

An `AgenticRun` is a custom Kubernetes object used by the Agentic Operator. It stores the workflow data as a persistent work record. Separate sandbox Pods perform each stage.

Read its two halves as a work order and a progress record:

<div className="article-table" tabIndex={0} role="region" aria-label="AgenticRun work order and progress record">

| Area | Meaning |
| --- | --- |
| `spec` | The work order. It contains the request, target namespace, stages, agents, and skills. |
| `status` | The progress record. It contains conditions and links to the analysis, execution, and verification result objects. |

</div>

The Adapter creates the work order. The Agentic Operator updates its progress as each stage finishes.

#### Example AgenticRun: the work order created from an alert

The Adapter generates this resource after an eligible alert fires. This example focuses on the fields that define the work.

```yaml
apiVersion: agentic.openshift.io/v1alpha1
kind: AgenticRun
metadata:
  name: serviceerrorratehigh-storefront-a1b2c3d4
  namespace: openshift-lightspeed
  labels:
    agentic.openshift.io/alert-name: serviceerrorratehigh
    agentic.openshift.io/alert-severity: critical
spec:
  request: |
    A Kubernetes alert is firing for storefront-api.
    Investigate the cause of the elevated service error rate.
  targetNamespaces:
    - storefront
  analysis:
    agent: default
  execution:
    agent: default
  verification:
    agent: default
```

<div className="article-table" tabIndex={0} role="region" aria-label="AgenticRun fields">

| Field | Meaning |
| --- | --- |
| `metadata.name` | Identifies this alert occurrence. The Adapter derives the name from alert details and start time so a repeated poll does not create a duplicate run. |
| `metadata.labels` | Records where the run came from and basic alert details. The Adapter uses labels when it checks for existing work. |
| `spec.request` | Gives the analysis stage a simple description of the alert to investigate. |
| `spec.targetNamespaces` | Names the namespaces that the run targets. The Operator uses these as context and for permission scoping. |
| `spec.analysis` | Defines the required investigation stage and the Agent custom resource that handles it. |
| `spec.execution` | Defines an optional action stage. Omit it for an analysis-only workflow. |
| `spec.verification` | Defines an optional check after execution. Omit it when the workflow does not need a verification stage. |
| `status` | Does not appear in this creation example. The Operator writes conditions and result references as the run progresses. |

</div>

The Adapter creates the record. From that point, the Operator owns the run lifecycle and updates its progress.

### 4. Lightspeed Agentic Operator: the coordinator

The Lightspeed Agentic Operator is a Kubernetes controller. A controller watches Kubernetes objects and works toward the requested state. This Operator reads the requested work in `spec` and the current progress in `status`.

For each run, the Operator finds the next stage and creates the sandbox Pod for that stage. It waits for the result, then updates the run's conditions. It also manages the approval object and the permissions used for an approved action.

The Operator manages the workflow. Sandbox Pods perform the investigation, action, and verification. The Adapter decides which alerts create runs, and a person chooses the remediation option.

### 5. ApprovalPolicy: the decision gate

An `ApprovalPolicy` assigns an approval mode to each workflow stage. The cluster-scoped policy must be named `cluster`.

#### Example ApprovalPolicy: set each stage's approval mode

In this example, analysis and verification start automatically. Execution waits for a person's approval.

```yaml
apiVersion: agentic.openshift.io/v1alpha1
kind: ApprovalPolicy
metadata:
  name: cluster
spec:
  stages:
    - name: Analysis
      approval: Automatic
    - name: Execution
      approval: Manual
    - name: Verification
      approval: Automatic
```

<div className="article-table" tabIndex={0} role="region" aria-label="ApprovalPolicy fields">

| Field | Meaning |
| --- | --- |
| `metadata.name: cluster` | Identifies the single cluster-wide policy. The API requires this name. |
| `spec.stages` | Lists the workflow stages whose approval behavior you want to define. |
| `name: Analysis` | Applies the rule to the investigation stage. |
| `name: Execution` | Applies the rule to the stage that can make a change. |
| `name: Verification` | Applies the rule to the post-action check. |
| `approval: Automatic` | Lets the Operator start that stage without a person approving it. |
| `approval: Manual` | Makes the Operator wait for explicit approval on an `AgenticRunApproval` resource. |

</div>

`Automatic` lets the Operator start a stage after the earlier stage finishes. `Manual` pauses the workflow for an administrator's decision. The policy controls stage timing; Kubernetes RBAC controls what an execution sandbox can read or change.

The current API treats any stage omitted from the policy as manual. A platform team can start with analysis only, then add an execution stage after it establishes a review process.

### 6. Sandbox workers: the temporary stage workers

A short-lived sandbox Pod handles one stage. It receives:

- an Agent definition and a connection to a large language model (LLM);
- a set of instructions called a skill, such as `investigate-alert`;
- a ServiceAccount that gives the Pod its Kubernetes identity and permissions;
- the request and related alert data for the current run.

<div className="article-table" tabIndex={0} role="region" aria-label="Agentic workflow stages">

| Stage or gate | What happens |
| --- | --- |
| Analysis sandbox | Uses the allowed cluster data to produce a diagnosis and possible options. |
| Approval gate | An administrator reviews the proposal and can select an action or deny it. |
| Execution sandbox | Runs only an approved action. Kubernetes RBAC limits the access available to the worker. |
| Verification sandbox | Starts after execution and checks the workload again. It returns checks and a pass or fail result. |

</div>

The Agentic Operator waits for the sandbox service to become ready, then sends the request for the current stage. The sandbox uses its Agent, skill, tools, and permissions and returns the result. The Operator saves that result in a Kubernetes object for the stage.

Analysis, execution, and verification use separate temporary workers. A skill guides the worker's task, while RBAC controls what the worker can read or change. Kubernetes can remove the temporary Pods and execution permissions after the run. The result objects remain available for review.

## Final thoughts

Alertmanager routes the alert, the Alerts Adapter creates the `AgenticRun`, and the Agentic Operator manages temporary workers for analysis, an approved action, and verification. These handoffs leave the evidence, decision, and result in one shared Kubernetes record for teams to review.

Review the `AgenticRun` conditions and results alongside logs, metrics, events, and change history before approving an action.
