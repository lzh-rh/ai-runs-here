Model Context Protocol (MCP) gives an AI application a standard way to discover and call tools. An MCP server supplies the tools. An MCP client, such as OpenShift Lightspeed, decides when to ask for one of them.

In this lab, you will connect OpenShift Lightspeed to MCP Gateway and list Pods in your cluster. The Gateway routes the tool call to an OpenShift MCP server, which reads the Pod data from the OpenShift API.

<McpGatewayOlsFlow />

If you want to see what happens inside the Gateway when Lightspeed lists or calls a tool, read [Understanding MCP Gateway and its request paths](https://lzh-rh.github.io/ai-runs-here/articles/how-mcp-gateway-works/).

You will deploy the MCP server, check its readiness, and test a tool call through the Gateway before connecting Lightspeed. These checkpoints help you locate a problem before adding the next component.

## 2. Deploy a read-only OpenShift MCP server

Give the MCP server a Kubernetes ServiceAccount, the identity its Pod will use to call the OpenShift API, and configure it for read-only tools.

### Create its ServiceAccount and guardrails

Use `vi` to save your first YAML file:

1. In your terminal, run `vi 01-openshift-mcp-prerequisites.yaml`.
2. Press <kbd>i</kbd> to enter insert mode.
3. Paste the YAML below. Keep the indentation as shown.
4. Press <kbd>Esc</kbd>, type `:wq!`, then press <kbd>Enter</kbd> to save the file and exit.

For later YAML files, repeat these steps with the filename shown. After saving each file, run its validation and apply commands.

Alternatively, create these resources from the OpenShift web console:

1. Click **Quick create (+)** in the upper-right corner and select **Import YAML**.
2. Paste the complete YAML block below, including the `---` separators. Keep the namespace values as shown.
3. Click **Create** and check for any errors.

If you use the console, skip the corresponding `oc apply -f` commands and continue with the permission checks below. Use this alternative for complete resource definitions, not the partial configuration fragments later in the lab.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: mcp-viewer
  namespace: mcp-exp
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: mcp-viewer-mcp-exp
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: mcp-viewer
    namespace: mcp-exp
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: openshift-mcp-server-config
  namespace: mcp-exp
data:
  config.toml: |
    log_level = 5
    port = "8080"
    read_only = true
    toolsets = ["core", "config"]
    cluster_auth_mode = "kubeconfig"
```

<div className="article-table" tabIndex={0} role="region" aria-label="OpenShift MCP server experiment settings">

| Setting | Meaning in this lab |
| --- | --- |
| `ServiceAccount/mcp-viewer` | Identifies the MCP server Pod. |
| `ClusterRoleBinding/mcp-viewer-mcp-exp` | Grants that ServiceAccount the cluster-wide `view` role through Kubernetes role-based access control (RBAC). |
| `read_only = true` | Limits the server to read-oriented MCP tools. |
| `cluster_auth_mode = "kubeconfig"` | Makes the server use its in-cluster ServiceAccount credentials for OpenShift API requests. The server's default is `passthrough`, so this lab sets `kubeconfig` explicitly. |

</div>

## 4. Configure and register the Gateway

Five Kubernetes objects describe this setup:

<div className="article-table" tabIndex={0} role="region" aria-label="MCP Gateway configuration objects">

| Object | Job |
| --- | --- |
| `GatewayClass` | Selects the OpenShift gateway controller |
| `Gateway` | Declares the client-facing `mcp` listener and backend-facing `mcps` listener |
| `MCPGatewayExtension` | Adds the MCP broker and router behavior |
| `HTTPRoute` | Points to the backend MCP Service |
| `MCPServerRegistration` | Adds the backend tools and the `openshift_` prefix |

</div>

### Create the Gateway

The `Gateway` uses two logical listeners on port 8080. Their names must be unique:

- `mcp` receives requests from MCP clients, including OpenShift Lightspeed.
- `mcps` accepts the internally rerouted requests for registered backend MCP servers.

Create the `Gateway`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: mcp-gateway-config
  namespace: openshift-ingress
data:
  service: |
    spec:
      type: ClusterIP
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: mcp-gateway
  namespace: openshift-ingress
spec:
  gatewayClassName: openshift-default
  infrastructure:
    parametersRef:
      group: ""
      kind: ConfigMap
      name: mcp-gateway-config
  listeners:
    - name: mcp
      hostname: mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local
      port: 8080
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: All
    - name: mcps
      hostname: "*.mcp.local"
      port: 8080
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: All
```

With the `mcp-gateway-config` ConfigMap, you tell the Gateway controller to create a `ClusterIP` Service. Lightspeed can use this internal cluster address to reach the Gateway. For the protocol check from your computer, you will open a temporary tunnel with `oc port-forward`.

Save it as `03-gateway.yaml`, then validate and apply it:

```bash
oc apply --dry-run=server -f 03-gateway.yaml
oc apply -f 03-gateway.yaml
oc wait gateway/mcp-gateway -n openshift-ingress \
  --for=condition=Programmed --timeout=5m
```

After you create the `Gateway`, its controller creates the Service. Find its name so you can check that the listener hostname matches its cluster address:

```bash
oc get service -n openshift-ingress \
  -l gateway.networking.k8s.io/gateway-name=mcp-gateway
```

This article expects `mcp-gateway-openshift-default`, which matches the hostname in the `mcp` listener. If your Service has another name, use `<service-name>.openshift-ingress.svc.cluster.local` wherever the lab uses this hostname. Update the `mcp` listener in `03-gateway.yaml` and reapply that file before continuing.

### Enable MCP processing

Create the extension and its cross-namespace permission:

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-mcp-gateway-extension
  namespace: openshift-ingress
spec:
  from:
    - group: mcp.kuadrant.io
      kind: MCPGatewayExtension
      namespace: mcp-gateway
  to:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: mcp-gateway
---
apiVersion: mcp.kuadrant.io/v1alpha1
kind: MCPGatewayExtension
metadata:
  name: mcp-gateway-extension
  namespace: mcp-gateway
spec:
  httpRouteManagement: Enabled
  privateHost: http://mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local:8080
  publicHost: mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local
  targetRef:
    group: gateway.networking.k8s.io
    kind: Gateway
    name: mcp-gateway
    namespace: openshift-ingress
    sectionName: mcp
```

Save it as `04-mcp-gateway-extension.yaml`, then validate, apply, and wait:

```bash
oc apply --dry-run=server -f 04-mcp-gateway-extension.yaml
oc apply -f 04-mcp-gateway-extension.yaml
oc wait mcpgatewayextension/mcp-gateway-extension -n mcp-gateway \
  --for=condition=Ready --timeout=5m
oc get httproute mcp-gateway-route -n mcp-gateway
```

The controller creates `HTTPRoute/mcp-gateway-route`. It sends client requests for `/mcp` to the broker.

### Register the OpenShift MCP server

Connect the backend Service to the Gateway and register its tools:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: mcp-server-test-route
  namespace: mcp-exp
  labels:
    mcp-server: "true"
spec:
  hostnames:
    - mcp-server-test.mcp.local
  parentRefs:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: mcp-gateway
      namespace: openshift-ingress
      sectionName: mcps
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /mcp
      backendRefs:
        - name: mcp-server-test
          port: 8080
---
apiVersion: mcp.kuadrant.io/v1alpha1
kind: MCPServerRegistration
metadata:
  name: mcp-server-test
  namespace: mcp-exp
spec:
  path: /mcp
  prefix: openshift_
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: mcp-server-test-route
```

Save it as `05-register-openshift-mcp.yaml`, then run:

```bash
oc apply --dry-run=server -f 05-register-openshift-mcp.yaml
oc apply -f 05-register-openshift-mcp.yaml
oc wait mcpserverregistration/mcp-server-test -n mcp-exp \
  --for=condition=Ready --timeout=5m

oc get mcpserverregistration mcp-server-test -n mcp-exp \
  -o jsonpath='ready={.status.conditions[?(@.type=="Ready")].status}{"\n"}'
```

You can give the `MCPServerRegistration` and `MCPServer` different names. This lab uses `mcp-server-test` for both to help you identify related resources. The registration's `targetRef` connects it to the `HTTPRoute`; the route's `backendRefs` points to the MCP server Service.

The broker adds the `openshift_` prefix to distinguish this server's tools in the combined catalog. For example, `pods_list_in_namespace` appears to clients as `openshift_pods_list_in_namespace`.

## 5. Prove the Gateway before editing OpenShift Lightspeed

### Open a local connection

Find the generated Gateway Service and start a local tunnel:

```bash
export MCP_GATEWAY_SERVICE="$(oc get service \
  -n openshift-ingress \
  -l gateway.networking.k8s.io/gateway-name=mcp-gateway \
  -o jsonpath='{.items[0].metadata.name}')"

oc port-forward -n openshift-ingress \
  service/"${MCP_GATEWAY_SERVICE}" 18080:8080
```

Keep that terminal open. In a second terminal, set the internal hostname:

```bash
export MCP_GATEWAY_HOST=mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local
```

### Initialize an MCP session

Run the remaining commands in the second terminal. Start the session:

```bash
curl --noproxy '*' -sS \
  -D /tmp/mcp-initialize.headers \
  -o /tmp/mcp-initialize.body \
  -w 'initialize HTTP=%{http_code}\n' \
  -X POST http://127.0.0.1:18080/mcp \
  -H "Host: ${MCP_GATEWAY_HOST}" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"gateway-lab","version":"1.0"}}}'

export MCP_SESSION_ID="$(awk 'BEGIN{IGNORECASE=1} /^mcp-session-id:/ {gsub("\r", "", $2); print $2}' /tmp/mcp-initialize.headers)"
test -n "${MCP_SESSION_ID}" && printf 'MCP session initialized.\n'
```

Tell the server that initialization is complete:

```bash
curl --noproxy '*' -sS -o /dev/null \
  -w 'initialized HTTP=%{http_code}\n' \
  -X POST http://127.0.0.1:18080/mcp \
  -H "Host: ${MCP_GATEWAY_HOST}" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -H "Mcp-Session-Id: ${MCP_SESSION_ID}" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
```

### List the tools and make a read-only call

Ask the Gateway for its tool list:

```bash
curl --noproxy '*' -sS \
  -o /tmp/mcp-tools.body \
  -w 'tools/list HTTP=%{http_code}\n' \
  -X POST http://127.0.0.1:18080/mcp \
  -H "Host: ${MCP_GATEWAY_HOST}" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -H "Mcp-Session-Id: ${MCP_SESSION_ID}" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'

grep -o 'openshift_[A-Za-z0-9_.-]*' /tmp/mcp-tools.body | sort -u
```

Continue only when `initialize` and `tools/list` return HTTP 200, the initialized notification returns a successful 2xx status, and at least one tool starts with `openshift_`.

Call one read-only tool through the same session:

```bash
curl --noproxy '*' -sS \
  -o /tmp/mcp-tool-call.body \
  -w 'tools/call HTTP=%{http_code}\n' \
  -X POST http://127.0.0.1:18080/mcp \
  -H "Host: ${MCP_GATEWAY_HOST}" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -H "Mcp-Session-Id: ${MCP_SESSION_ID}" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"openshift_pods_list_in_namespace","arguments":{"namespace":"mcp-exp"}}}'

cat /tmp/mcp-tool-call.body
```

Checkpoint: expect `tools/call HTTP=200` and inspect `/tmp/mcp-tool-call.body` for the Pod list. Continue after you confirm the tool returned data, since HTTP 200 alone does not rule out an MCP error.

Press <kbd>Ctrl</kbd>+<kbd>C</kbd> in the first terminal to close the local tunnel. Lightspeed will use the internal Gateway address, so it does not need this tunnel.

## 6. Connect OpenShift Lightspeed

OpenShift Lightspeed has a built-in cluster-introspection path when `spec.ols.introspectionEnabled` is true. This lab adds a second path:

```text
Built-in path
OLS -> Operator-managed OpenShift MCP server -> OpenShift API

Custom path in this lab
OLS -> MCP Gateway -> registered OpenShift MCP server -> OpenShift API
```

Leave the built-in path unchanged for the first test. Ask Lightspeed to use the `openshift_` tool from the Gateway catalog.

Back up the existing object locally:

```bash
oc get olsconfig cluster -o yaml > olsconfig-before-mcp-gateway.yaml
```

Do not commit this backup. It can contain internal configuration references.

Edit the existing object:

```bash
oc edit olsconfig cluster
```

Merge this fragment under the existing `spec`:

```yaml
spec:
  featureGates:
    - MCPServer
  mcpServers:
    - name: openshift-mcp-gateway
      url: http://mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local:8080/mcp
      timeout: 30
```

Add these entries to your existing configuration, preserving `spec.llm`, `spec.ols`, other feature gates, and MCP servers. Include `MCPServer` once in the feature-gate list. The `url` points Lightspeed to the internal Gateway endpoint.

Wait for the app server:

```bash
oc rollout status deployment/lightspeed-app-server \
  -n openshift-lightspeed --timeout=10m
```

Start a new OpenShift Lightspeed conversation and request the same Pod list:

```text
Use openshift_pods_list_in_namespace to list pods in mcp-exp. Do not create, update, or delete anything.
```

Approve only a read-only tool whose name and arguments match the request.

The final checkpoint needs two pieces of evidence:

- the protocol test returned one or more `openshift_` tools through MCP Gateway;
- OpenShift Lightspeed called an `openshift_` tool and returned pod data from `mcp-exp`.

### Optional: use only the Gateway path

After the custom path works, you can disable the built-in OpenShift MCP server to make the Gateway Lightspeed's sole source of cluster tools. Edit `OLSConfig`:

```bash
oc edit olsconfig cluster
```

Merge this value into the existing `spec.ols` section and preserve its other fields:

```yaml
spec:
  ols:
    introspectionEnabled: false
```

Keep the custom `spec.mcpServers` entry that points to MCP Gateway.
