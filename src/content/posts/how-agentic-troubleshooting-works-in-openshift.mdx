An OpenShift alert tells you that something may be wrong. It may not show the cause or the safest fix. In this lab, you follow an alert, review the evidence, approve an optional fix, and check the result.

Agentic troubleshooting uses Kubernetes objects that you can inspect. The system investigates an alert, suggests a fix, waits for approval, applies only the approved change, and checks the workload again.

This article follows the [OpenShift 5 Early Access showroom exercise](https://rhpds.github.io/ocp5-ea-showroom/modules/agentic-troubleshooting.html). It uses the example and Alerts Adapter settings from that exercise.

## Start with a simple mental model

Think of the workflow as a support ticket:

1. An alert reports a problem.
2. The Alerts Adapter opens a work order named AgenticRun.
3. The Agentic Operator sends short-lived sandbox pods to investigate the problem.
4. You review and approve an optional fix.
5. A separate sandbox pod checks the workload after the fix.

The later sections explain each part of this flow.

## Prepare your environment

You need:

- Access to the prepared OpenShift 5 Early Access showroom environment.

- Access to the OpenShift web console and the `oc` command-line tool.

- Permission to view alerts and Agentic resources in `openshift-lightspeed`.

- Permission to edit `ConfigMap/alerts-adapter-config` and restart its Deployment for the alert-triggered exercise.

The showroom already includes the sample applications, monitoring rules, Alerts Adapter, Agentic Operator, sandbox settings, and planned payment failure. Resource names and behavior may differ on another cluster.

### Allow the adapter to process the alert

The Early Access adapter starts with no allowed Alertmanager receivers. A receiver is a named route that sends a group of alerts to a target. An administrator must allow a receiver before its alerts can create runs.

Back up the current adapter settings, edit them, and restart the adapter:

```bash
oc -n openshift-lightspeed get configmap alerts-adapter-config \
  -o jsonpath='{.data.config\.yaml}' \
  > /tmp/alerts-adapter-config.before.yaml

oc -n openshift-lightspeed edit configmap alerts-adapter-config

oc -n openshift-lightspeed rollout restart \
  deployment/lightspeed-agentic-alerts-adapter
```

The first command saves the current `config.yaml` value in `/tmp`. The second command opens the ConfigMap in your text editor. The last command restarts the adapter so that it reads the new settings.

Under `filtering.allowedReceivers`, enable `critical`:

```yaml
filtering:
  allowedReceivers:
    - critical
```

`critical` is the name of an **Alertmanager receiver**. An alert sent to this receiver can create a run when it matches the adapter rules. During my OpenShift 5.0.0-ec.6 test, this receiver created runs for the payment alert and an unrelated `ClusterOperatorDown` alert.

<ArticleCallout variant="caution" title="Review every generated run">
  Enabling a receiver can create runs for several alerts that match the adapter rules. Review every generated run before approving any action.
</ArticleCallout>

### Open the generated investigation

The adapter checks Alertmanager at set intervals. After its next check, go to **Administrator → Agentic Runs → Agentic runs**. Open the run for `PaymentErrorRateHigh`.

The run first shows that analysis is in progress. After analysis finishes, the run moves to the `Proposed` state. It shows the diagnosis, evidence, and possible fixes. At this point, the analysis sandbox has **not** changed the workload.

You can also view the same objects from the command line:

```bash
oc -n openshift-lightspeed get agenticruns

export ALERT_RUN="replace-with-payment-run-name"
oc -n openshift-lightspeed get agenticrun "$ALERT_RUN" -o yaml
oc -n openshift-lightspeed get analysisresults \
  -l agentic.openshift.io/run="$ALERT_RUN"
```

The first command lists all runs. Replace `replace-with-payment-run-name` with the name of the payment run. The last two commands show the full run and its analysis result.

Look at these fields:

- `spec.targetNamespaces` lists the namespaces that the run can investigate.
- `status.conditions` shows the run's progress.
- `status.steps.analysis.results` points to the saved analysis result.

  The payment run contains an analysis result and possible fixes, but execution has not started.
</ArticleCallout>

### Review, approve, and verify the optional fix

In the lab, review the proposed change from `reporting-service` version `v1.0.2` to `v1.0.1`. Check the evidence, target, commands, requested permissions, rollback plan, and verification plan. Then select **Execute remediation** and confirm the action.

The lab uses this approval policy:

1. An analysis sandbox investigates and proposes options.
2. The workflow stops at the approval gate.
3. Your approval selects one option. The Operator limits the permissions to that action.
4. An execution sandbox receives those temporary permissions. Kubernetes calls this permission system role-based access control (RBAC).
5. A different verification sandbox checks the workload again.

During my OpenShift 5.0.0-ec.6 test, the execution ServiceAccount could update only `deployment/reporting-service`. A ServiceAccount is the Kubernetes identity used by a pod. It could read ReplicaSets, which record Deployment versions. It could not update `payments-api` or list Secrets. The verification stage then confirmed image `v1.0.1`, readiness `1/1`, working HTTP responses, and cleared payment alerts.

Check the cluster yourself. A successful agent response is only one piece of evidence:

```bash
oc -n payments get deployment reporting-service
oc -n payments logs deployment/payments-api --since=2m

oc -n openshift-lightspeed get executionresults,verificationresults \
  -l agentic.openshift.io/run="$ALERT_RUN"
```

The first command checks the Deployment. The second reads recent application logs. The last command shows the saved execution and verification results for this run.

Restore the adapter settings that you backed up so future alerts do not start more lab runs:

```bash
oc -n openshift-lightspeed set data \
  configmap/alerts-adapter-config \
  --from-file=config.yaml=/tmp/alerts-adapter-config.before.yaml

oc -n openshift-lightspeed rollout restart \
  deployment/lightspeed-agentic-alerts-adapter
```

The first command restores the saved file. The second restarts the adapter with the restored settings.

Review every run created while `critical` was enabled. If you did not want a run, deny its proposal instead of approving it.

<ArticleCallout variant="checkpoint" title="Checkpoint">
  The target workload is healthy, the verification result is saved, and the original adapter settings are restored.
</ArticleCallout>

## Understand what happens behind the scenes

The Kubernetes API is where components read and save Kubernetes objects. It provides the handoff between the adapter and the Agentic Operator.

<AgenticWorkflow />

Read the numbered arrows from top to bottom:

1. **Alertmanager → Alerts Adapter:** The adapter checks Alertmanager at set intervals for active alerts.
2. **Alerts Adapter → AgenticRun:** For each alert that matches its rules, the adapter creates a Kubernetes work order.
3. **AgenticRun → Agentic Operator:** The Operator watches the work order through the Kubernetes API.
4. **Agentic Operator → analysis sandbox:** The Operator creates a temporary worker to investigate and propose options.
5. **Analysis → approval gate:** The proposal waits when the `ApprovalPolicy` requires a person to decide.
6. **Agentic Operator → execution sandbox:** After approval, the Operator creates a new worker. RBAC gives this worker temporary permissions for the approved action.
7. **Agentic Operator → verification sandbox:** After execution, the Operator creates a separate worker to check recovery.

Each sandbox returns a result object for its stage. The Operator saves these results and the run's conditions in the Kubernetes API.

The adapter creates the work order in the Kubernetes API. The Operator watches the work order and creates the sandbox pods. The adapter and sandbox pods do not need a direct connection because they share information through the API.

### Agentic Alerts Adapter: the translator

Think of the adapter as an intake clerk. The [Alerts Adapter repository](https://github.com/openshift/lightspeed-agentic-alerts-adapter) includes an `ARCHITECTURE.md` file that explains its design. The adapter:

1. checks the Alertmanager API inside the cluster for firing alerts;
2. checks each alert's receiver, severity, age, and previous runs;
3. creates one `AgenticRun` in `openshift-lightspeed` for each alert that matches the rules.

Polling means checking for new data at set intervals. This lets the adapter find an alert that is still firing after a restart. On each check, the adapter reads current alerts and existing runs. It does not keep its own database. After it creates a run, the Agentic Operator manages the remaining steps.

The adapter copies useful alert details into the run. These details include the alert name, severity, summary, start time, unique identifier, affected namespace, and investigation request. The adapter also adds the chosen agent and skill settings.

The adapter does **not** diagnose the incident, call the large language model (LLM), create a sandbox, approve a proposal, or change the workload.

#### Read the adapter Deployment YAML

The adapter's `Deployment` shows where and how the adapter runs. The `alerts-adapter-config` ConfigMap shows which alerts it handles and how often it checks them. The ConfigMap appears later in this article.

The following example is based on the architecture documented in the [Alerts Adapter repository](https://github.com/openshift/lightspeed-agentic-alerts-adapter). I also compared it with the Early Access deployment template. The example shows how the parts in this article connect. To deploy the adapter, use the installation manifest.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lightspeed-agentic-alerts-adapter
  namespace: openshift-lightspeed
spec:
  replicas: 1
  selector:
    matchLabels:
      app: lightspeed-agentic-alerts-adapter
  template:
    metadata:
      labels:
        app: lightspeed-agentic-alerts-adapter
    spec:
      serviceAccountName: lightspeed-agentic-alerts-adapter
      containers:
        - name: adapter
          image: quay.io/openshift-lightspeed/lightspeed-agentic-alerts-adapter:latest
          env:
            - name: ALERTMANAGER_URL
              value: https://alertmanager-main.openshift-monitoring.svc:9094
          volumeMounts:
            - name: config
              mountPath: /etc/alerts-adapter
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: alerts-adapter-config
```

<div className="article-table" tabIndex={0} role="region" aria-label="Adapter Deployment fields">

| Important field | Why it matters |
| --- | --- |
| `namespace:` `openshift-lightspeed` | Places the adapter beside the Agentic components in this environment. |
| `replicas:` `1` | Runs one adapter pod. After a restart, the pod reads the alerts and existing runs from the APIs again. It does not need a local database. |
| `selector.matchLabels` and `template.metadata.labels` | The matching label lets the Deployment identify and manage its pod. |
| `serviceAccountName` | Gives the pod a Kubernetes identity. RBAC rules let this identity read alerts and create or list `AgenticRun` objects. |
| `image` | Selects the adapter program. The installation manifest supplies the image to use. The architecture example uses `latest` as a readable sample value. |
| `ALERTMANAGER_URL` | Gives the adapter the address of the Alertmanager service inside the cluster. The adapter checks this service for firing alerts. |
| `configMap`, `mountPath`, and `readOnly` | Places `alerts-adapter-config` inside the container at `/etc/alerts-adapter`. The `readOnly` setting stops the container from changing the mounted files. |

</div>

This YAML starts the adapter. The ConfigMap you edit during the exercise selects the `critical` receiver.

### AgenticRun: the work order

An AgenticRun is a custom Kubernetes object added by the Agentic Operator. It stores the workflow data in the Kubernetes API. The Agentic Operator and sandbox pods read and update that data.

Read its two halves as a work order and progress record:

<div className="article-table" tabIndex={0} role="region" aria-label="AgenticRun fields">

| Area | Meaning |
| --- | --- |
| `spec` | The work order. It contains the request, target namespace, stages, agents, and skills. |
| `status` | The progress record. It contains conditions and links to the analysis, execution, and verification result objects. |

</div>

The adapter creates the work order. The Agentic Operator updates its progress as each stage finishes.

### Lightspeed Agentic Operator: the coordinator

The Lightspeed Agentic Operator is a Kubernetes controller. A controller watches Kubernetes objects and works toward the requested state. This Operator reads the requested work in `spec` and the current progress in `status`.

For each run, the Operator finds the next stage and creates the sandbox pod for that stage. It waits for the result and then updates the run's conditions. It also manages the approval object and temporary permissions for the fix. In this lab, analysis starts on its own, execution waits for your approval, and verification starts after execution.

The Operator manages the workflow. Sandbox pods perform the investigation, fix, and verification.

#### How the ApprovalPolicy controls the gates

The [Agentic Operator](https://github.com/openshift/lightspeed-agentic-operator) reads an `ApprovalPolicy`. This policy says whether a stage can start on its own or must wait for a person. This lab uses these settings:

```yaml
apiVersion: agentic.openshift.io/v1alpha1
kind: ApprovalPolicy
metadata:
  name: cluster
  namespace: openshift-lightspeed
spec:
  stages:
    - name: Analysis
      approval: Automatic
    - name: Execution
      approval: Manual
    - name: Verification
      approval: Automatic
```

`Automatic` lets the Operator start a stage after the earlier stage has finished. `Manual` pauses the workflow for an administrator's decision. In this lab, the Operator starts analysis, waits for approval before execution, and starts verification after execution. The policy controls when a stage can start. You choose the fix, and Kubernetes RBAC limits what the execution sandbox can change.

### Sandbox pods: the temporary workers

A sandbox pod is a short-lived worker for one stage. It receives:

- an agent definition and a connection to a large language model (LLM);
- a set of instructions called a skill, such as [investigate-alert](https://github.com/openshift/agentic-skills/tree/main/cluster-troubleshoot/investigate-alert);
- a ServiceAccount that gives the pod its Kubernetes identity and permissions;
- the request and related alert data for the current run.

<div className="article-table" tabIndex={0} role="region" aria-label="Agentic workflow stages">

| Stage or gate | What happens |
| --- | --- |
| Analysis sandbox | Uses the allowed cluster data to produce a diagnosis and possible fixes. The Operator prepares temporary permissions for the execution sandbox. |
| Approval gate | An administrator reviews the proposal. The administrator can select an action or deny it. |
| Execution sandbox | Runs only the approved fix. Its temporary RBAC allows only the selected action. |
| Verification sandbox | Starts after execution and checks the workload again. It returns a list of checks and a pass or fail result. |

</div>

The Agentic Operator waits for the sandbox service to become ready. It then sends the request for the current stage. The sandbox uses its agent, skill, tools, and permissions and returns the result. The Operator saves the result in a Kubernetes object for that stage.

Analysis, execution, and verification use separate temporary workers. A skill tells a worker how to investigate. RBAC controls what the worker can read or change. Kubernetes can remove the temporary pods and execution permissions after the run. The result objects remain so that you can review what happened.

## Understand the Alerts Adapter configuration

The configuration contains **two YAML documents**:

1. The outer document creates a Kubernetes `ConfigMap`.
2. The `data.config.yaml` value contains the adapter's YAML as text.

This is the configuration used in the test after enabling the `critical` receiver. Comments are removed to keep the example short:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: alerts-adapter-config
  namespace: openshift-lightspeed
data:
  config.yaml: |
    pollInterval: 30s
    postRunDelay: 1h
    filtering:
      allowedReceivers:
        - critical
    analysis:
      tools:
        skills:
          - image: quay.io/openshiftanalytics/agentic-skills:latest
            paths:
              - /skills/cluster-troubleshoot/investigate-alert
```

### The outer ConfigMap

<div className="article-table" tabIndex={0} role="region" aria-label="ConfigMap fields">

| Field | Meaning |
| --- | --- |
| `apiVersion:` `v1` | Uses the main Kubernetes API version for a ConfigMap. |
| `kind:` `ConfigMap` | Stores settings that are not secret. Store passwords and tokens in a Secret instead. |
| `metadata.name` | Names the object `alerts-adapter-config`. The Deployment expects this name. |
| `metadata.namespace` | Places it beside the adapter in `openshift-lightspeed`. |
| `data` | Starts the ConfigMap's key and value section. |
| `config.yaml` | Creates a key named `config.yaml`. The vertical bar after `config.yaml:` tells Kubernetes to store the indented lines as one block of text. The adapter reads that text as its own YAML document. |

</div>

### The inner `config.yaml`

<div className="article-table" tabIndex={0} role="region" aria-label="Alerts Adapter settings">

| Field and test value/default | What it controls |
| --- | --- |
| `pollInterval` (`30s`) | How often the adapter asks Alertmanager for firing alerts. It does not control how long the investigation takes. |
| `preRunDelay` (not set; default `0s`) | The minimum time an alert must stay active. The commented `5m` example does not apply. A delay can ignore short alerts. |
| `postRunDelay` (`1h`) | After a run for the same problem reaches Completed, Failed, Denied, or Escalated, the adapter waits one hour before it can create another run. The timer starts when the run enters that final state. The adapter matches the problem by its stable fingerprint. |
| `filtering` (section) | Groups alert selection settings. |
| `filtering.allowedReceivers` (empty until the lab enables `critical`) | Lists the Alertmanager receivers that the adapter accepts. An empty list creates no runs. Letter case does not matter. The adapter also skips severity `none` and `info`. |
| `deduplication` (optional section) | Groups settings that help the adapter avoid duplicate runs for the same problem. |
| `deduplication.ignoredLabels` (not set; defaults to `pod`, `instance`, `endpoint`, `uid`) | Leaves changing labels out of the problem identifier. This stops a new pod name from looking like a new problem. Your list replaces the defaults. An empty list (`[]`) uses every label. |
| `tools.skills` (not set) | Lists skills that all stages can use. Each item needs a container image and one or more paths to skill files in that image. |
| `agent.default` (not set; uses `default`) | Sets an optional agent name for all stages. |
| `agent.analysis`, `agent.execution`, `agent.verification` (not set) | Set an optional agent for one stage. A stage setting replaces `agent.default` for that stage. |
| `analysis.tools.skills` (one `investigate-alert` skill) | Adds the skill only to the analysis stage. A stage tool setting replaces the shared tools for that stage. |
| `analysis.tools.skills[].image` (`quay.io/openshiftanalytics/agentic-skills:latest`) | Names the container image that holds the skill files. For repeatable results, use a fixed version tag or an exact image digest instead of the moving `latest` tag. |
| `analysis.tools.skills[].paths` (`/skills/cluster-troubleshoot/investigate-alert`) | Gives the path to the skill directory inside the image. The analysis worker uses files from this directory. |
| `execution.tools.skills`, `verification.tools.skills` (not set) | Can set different skills for execution or verification. The template shows only commented examples, so these stages get no extra skill unless an administrator enables one. |

</div>

The YAML parser ignores text after a hash symbol (`#`). A commented `preRunDelay` does not change the default delay. A commented `critical` entry does not enable that receiver.

### How these fields become an AgenticRun

For each alert that matches its rules, the adapter copies data into an AgenticRun:

<div className="article-table" tabIndex={0} role="region" aria-label="Alert to AgenticRun field mapping">

| Input | Generated run field |
| --- | --- |
| Alert identification details | Run name, labels, and annotations. They connect the run to the original alert. The name and labels also help avoid duplicate runs. |
| Alert `namespace` label | `spec.targetNamespaces`; the `AgenticRun` remains in `openshift-lightspeed`. |
| Alert investigation details | A `spec.request` that asks the analysis agent to investigate. |
| `agent.*` | `spec.analysis.agent`, `spec.execution.agent`, and `spec.verification.agent` |
| Shared `tools.skills` | `spec.tools.skills` |
| Tool settings for one stage | `spec.analysis.tools`, `spec.execution.tools`, or `spec.verification.tools` |

</div>

The adapter and Agentic Operator use the AgenticRun as their shared work record. They exchange information through the Kubernetes API instead of a direct connection. You can inspect the same record with Kubernetes tools.

## Final thoughts

Agentic troubleshooting uses clear handoffs. The Alerts Adapter creates an AgenticRun for a matching alert. The Agentic Operator then manages temporary workers that investigate the problem, apply an approved fix, and check the result. You can inspect each step through Kubernetes objects.

I tested this workflow on OpenShift 5.0.0-ec.6. Review the evidence before approving a fix, and use an environment where you have permission to make and undo changes. Follow the [OpenShift 5 Early Access Agentic troubleshooting exercise](https://rhpds.github.io/ocp5-ea-showroom/modules/agentic-troubleshooting.html) to try the complete workflow.
