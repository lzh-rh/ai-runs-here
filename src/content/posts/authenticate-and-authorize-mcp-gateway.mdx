You can use your existing MCP Gateway to list OpenShift Pods. In this lab, you will add two checks before the gateway forwards a request:

1. **Authentication:** verify the caller's access token.
2. **Authorization:** check whether the caller has permission to run the tool.

You will create two Keycloak users, `mcp-reader` and `mcp-no-tools`, and test the same Pod-list tool with each from a terminal. Both can sign in, but you will give only `mcp-reader` the role needed to run the tool.

## What you will learn

- The difference between authentication (who is calling) and authorization (what they may do).
- How a Keycloak JSON Web Token (JWT) carries a user's identity and roles to the gateway.
- How the gateway checks tool roles to decide whether a user may run an MCP tool.
- Why a user's gateway permissions are separate from the backend's OpenShift role-based access control (RBAC) permissions.

## Before you begin

Use a gateway with no active clients or shared user traffic. You will change its access rules so that clients need a Keycloak token to use `/mcp`.

## Architecture at a glance

### Understand the two identities

Think of a secure office:

- **Keycloak is the badge office.** You sign in to get a signed access token, the JWT.
- **Authentication is the front-door guard.** It checks whether the badge is genuine.
- **Authorization is the room guard.** It checks whether your badge grants access to the requested MCP tool.

The backend has a separate identity for OpenShift: its `mcp-viewer` **ServiceAccount**, an account for a workload. You use OpenShift RBAC to set what that account may read or change.

A **listener** is a named entry point on the Gateway. You will attach an **AuthPolicy**, a set of access rules, to each listener. **Authorino** is the Connectivity Link component that evaluates those rules.

<McpGatewayAuthFlow />

Read the flow in order:

1. You sign in to Keycloak and receive a signed JWT. The reader's JWT contains the tool role; the no-tools user's JWT does not.
2. The client sends that token with an MCP request to the `mcp` listener.
3. At `mcp`, Authorino validates the token using the first `AuthPolicy`. The gateway returns HTTP 401 for a missing, expired, or invalid token.
4. The MCP router reads the tool call and identifies the backend registration and unprefixed tool name.
5. At `mcps`, Authorino checks those values against the JWT roles using the second `AuthPolicy`. The gateway denies the call if the user lacks the tool role.
6. The OpenShift MCP server uses `ServiceAccount/mcp-viewer` for its OpenShift API request.
7. The OpenShift API checks that ServiceAccount's RBAC permissions before returning data.

### 1.9 Request and inspect the reader JWT

In terminal 2, set and verify the realm address:

```bash
export KEYCLOAK_ISSUER="https://${KEYCLOAK_HOST}/realms/mcp-auth-lab"

curl -fsS "${KEYCLOAK_ISSUER}/.well-known/openid-configuration" \
  | jq '{issuer, token_endpoint}'
```

The **issuer** is the address of your Keycloak realm. The **token endpoint** is the URL that accepts your token request. Check that `issuer` exactly matches `KEYCLOAK_ISSUER` and `token_endpoint` is that address followed by `/protocol/openid-connect/token` before sending credentials.

Open **Clients > mcp-gateway > Credentials** in Keycloak. Use the copy icon beside **Client Secret**; do not click **Regenerate**.

<ArticleImage
  src="/images/mcp-gateway-auth/03-client-credentials.webp"
  width={2000} height={1019}
  alt="The mcp-gateway Credentials tab shows a masked Client Secret with a copy icon beside it."
  caption="Copy the current Client Secret using the copy icon, not Regenerate."
/>

Run this command in terminal 2, paste the secret, and press <kbd>Enter</kbd>. The terminal hides your input.

```bash
IFS= read -rs KEYCLOAK_CLIENT_SECRET
```

Next, run this command, enter the `mcp-reader` password, and press <kbd>Enter</kbd>:

```bash
IFS= read -rs MCP_READER_PASSWORD
```

Confirm both values were entered without displaying them:

```bash
test -n "${KEYCLOAK_CLIENT_SECRET}" && echo 'Client secret entered'
test -n "${MCP_READER_PASSWORD}" && echo 'Reader password entered'
```

Run one input command at a time and enter its value before continuing. Check for both confirmation messages. `read -rs` keeps the value hidden and preserves backslashes. Use this form in Bash or zsh; `read -p` has a different meaning in zsh.

Request a token:

```bash
TOKEN_RESPONSE="$(curl -sS \
  "${KEYCLOAK_ISSUER}/protocol/openid-connect/token" \
  --data-urlencode 'grant_type=password' \
  --data-urlencode 'client_id=mcp-gateway' \
  --data-urlencode "client_secret=${KEYCLOAK_CLIENT_SECRET}" \
  --data-urlencode 'username=mcp-reader' \
  --data-urlencode "password=${MCP_READER_PASSWORD}" \
  --data-urlencode 'scope=openid profile')"

printf '%s\n' "${TOKEN_RESPONSE}" \
  | jq 'if .access_token
        then {token_received:true,token_type,expires_in,scope}
        else {error,error_description}
        end'
```

`--data-urlencode` encodes each form value. We omit `curl -f` here so Keycloak's useful JSON error remains visible. The filtered output does not print the token.

Expected: `token_received` is `true`. `expires_in` reports the access token's lifetime in seconds; it depends on your Keycloak settings. Resolve any error before continuing:

<div className="article-table" tabIndex={0} role="region" aria-label="Token request troubleshooting">

| Response | Check in Keycloak |
| --- | --- |
| `invalid_client`, or `unauthorized_client` with invalid client credentials | Select `mcp-auth-lab`; check client ID `mcp-gateway`, Client authentication On, and the current secret on Credentials. |
| Client not allowed to use Direct Access Grants | Turn Direct access grants on and save. |
| `invalid_grant: Invalid user credentials` | Check username, password, enabled state, and selected realm. |
| `invalid_grant: Account is not fully set up` | Fill first name, last name, and email; turn Temporary off; resolve remaining required actions. |

</div>

If you entered the wrong client secret, repeat the hidden prompts and token request. Use the existing secret on the Credentials page.

Store the token in memory and clear the temporary credentials:

```bash
export MCP_READER_TOKEN="$(printf '%s' "${TOKEN_RESPONSE}" \
  | jq -r '.access_token // empty')"
unset TOKEN_RESPONSE KEYCLOAK_CLIENT_SECRET MCP_READER_PASSWORD

test -n "${MCP_READER_TOKEN}" && echo 'Reader token received'
```

A JWT contains named values called **claims**. Inspect the issuer, username, and roles:

```bash
python3 -c 'import os,base64,json
p=os.environ["MCP_READER_TOKEN"].split(".")[1]
p += "=" * (-len(p) % 4)
d=json.loads(base64.urlsafe_b64decode(p))
print(json.dumps({"iss":d.get("iss"),"preferred_username":d.get("preferred_username"),"resource_access":d.get("resource_access",{})},indent=2))'
```

You have decoded the JWT payload without checking its signature. Authorino checks the signature when you call the protected gateway.

**Checkpoint:** the issuer ends in `/realms/mcp-auth-lab`, the username is `mcp-reader`, and `resource_access["mcp-exp/mcp-server-test"].roles` contains `tool:pods_list_in_namespace`. If the role is missing, recheck 1.7 and 1.8 and request a new token. An already-issued JWT does not change when you assign a role.

### 2.2 Set the non-secret addresses

Run in terminal 2:

```bash
export KEYCLOAK_HOST="$(oc get route keycloak -n keycloak \
  -o jsonpath='{.spec.host}')"
export KEYCLOAK_ISSUER="https://${KEYCLOAK_HOST}/realms/mcp-auth-lab"
export MCP_GATEWAY_HOST='mcp-gateway-openshift-default.openshift-ingress.svc.cluster.local'
export MCP_GATEWAY_BASE="http://${MCP_GATEWAY_HOST}:8080"
export MCP_RESOURCE="${MCP_GATEWAY_BASE}/mcp"
export MCP_METADATA_URL="${MCP_GATEWAY_BASE}/.well-known/oauth-protected-resource"

printf 'Keycloak issuer: %s\nProtected MCP URL: %s\n' \
  "${KEYCLOAK_ISSUER}" "${MCP_RESOURCE}"
```

These are addresses, not credentials. The hostname matches the gateway's `mcp` listener. The tunnel uses `127.0.0.1`, but the HTTP `Host` header must still identify that listener.

### 2.3 Publish the OAuth discovery document

You publish a small JSON document so clients can find the Keycloak realm that issues tokens for this gateway. This is **OAuth discovery**. You will add the authentication check in 2.4.

Confirm the extension's field exists, then set it:

```bash
oc explain mcpgatewayextension.spec.oauthProtectedResource

export OAUTH_METADATA_PATCH="$(jq -nc \
  --arg resource "${MCP_RESOURCE}" \
  --arg issuer "${KEYCLOAK_ISSUER}" \
  '{spec:{oauthProtectedResource:{
    resourceName:"MCP Gateway",
    resource:$resource,
    authorizationServers:[$issuer],
    bearerMethodsSupported:["header"],
    scopesSupported:["openid","profile","roles"]
  }}}')"

oc patch mcpgatewayextension mcp-gateway-extension \
  -n mcp-gateway --type=merge -p "${OAUTH_METADATA_PATCH}"
oc rollout status deployment/mcp-gateway -n mcp-gateway --timeout=2m

oc get mcpgatewayextension mcp-gateway-extension -n mcp-gateway \
  -o jsonpath='{.spec.oauthProtectedResource}' | jq .
```

| Field | Meaning |
| --- | --- |
| `resource` | The MCP URL you want to protect. |
| `authorizationServers` | The Keycloak realm that issues tokens. |
| `bearerMethodsSupported: ["header"]` | Send the JWT in `Authorization: Bearer ...`. |
| `scopesSupported` | Named sets of information or access that clients can request, such as `profile`. |

</div>

Use the extension to configure these values. Its controller manages the broker/router Deployment and can overwrite edits you make to the Deployment's environment variables. See the [v0.7.1 authentication guide](https://github.com/Kuadrant/mcp-gateway/blob/v0.7.1/docs/guides/authentication.md).

## 3. Allow one tool and check the backend's permissions

The gateway checks whether the user may call the tool. The backend then uses its own OpenShift permissions to read the Pods.

### 3.1 Apply the internal tool-authorization policy

Open `02-authorization.yaml.tmpl`. It attaches to `mcps`, the listener the router uses for registered backend servers.

```bash

```

Continue only when it prints `Authorization YAML is ready`. Validate before applying:

```bash

```

If the dry run succeeds:

```bash

  --for=condition=Enforced --timeout=2m
```

At this listener, Authorino validates the JWT and checks the tool role if the router supplies a tool-name header.

For this call, the router supplies:

```text
x-mcp-servername: mcp-exp/mcp-server-test
x-mcp-toolname: pods_list_in_namespace
```

Read the permission check in four steps:

1. Read `pods_list_in_namespace`.
2. Add `tool:` to form `tool:pods_list_in_namespace`.
3. Open the JWT's `resource_access["mcp-exp/mcp-server-test"]` section.
4. Allow the call only if its `roles` list contains that role.

The router adds these headers; you do not need to type them. The policy uses HTTP 401 for an invalid identity and HTTP 403 for a valid identity without permission. In 4.3, you will check the logs if the gateway wraps the denial in an HTTP 500 response.

Next, run this command, enter the `mcp-no-tools` password, and press <kbd>Enter</kbd>. Input remains hidden in both commands.

## Final thoughts

Authentication checks who is calling. Authorization decides what they may do. Both users could sign in, but only `mcp-reader` had the role needed to run the Pod-list tool.

The backend's OpenShift permissions are separate. It uses `mcp-viewer` to access the cluster, and that ServiceAccount's RBAC permissions allow it to list Pods, but not delete them. Giving a user a tool role does not grant the backend more OpenShift permissions.
